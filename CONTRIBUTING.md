# Contributing

Thank you for your interest in contributing to the BMAD Plugin for Claude Code.

## Branching Model

`main` is the trunk. The Claude Code plugin marketplace installs from
the default branch with no option to pick another, so **every commit on
`main` is immediately live for users** — `main` must always be in a
releasable state.

```text
feature-branch → PR → main → tag release
```

| Branch | Purpose |
|---|---|
| `main` | Trunk and release branch. What users install. |
| `dev` | Historical. Retained but unmaintained — 51 commits behind `main` with nothing of its own. Do not branch from it. |
| `<type>/<concern>` | One concern per branch. Branch from `main`. |

> An earlier revision of this document described a Git Flow in which PRs
> merged to `dev`. That is not what the repository does: every merged PR
> to date targeted `main`. The document has been corrected rather than
> the practice.

### Stacked pull requests

A change that spans several concerns ships as a **stack** of one-concern
PRs, each of which passes its own gates alone:

```sh
gh stack init --base main chore/first-layer
# …commit…
gh stack add feat/second-layer
# …commit…
gh stack submit --auto --open      # push + open PRs, ready for review
gh stack view --json               # inspect
```

Put foundational changes (scripts, schemas) in lower layers and their
consumers (generated content, docs) above. To change a lower layer after
the fact: `gh stack down`, commit there, `gh stack rebase --upstack`.

### Rules

- **Never push directly to `main`** — always open a PR.
- **PR target is `main`.**
- **Do not squash** when merging — preserve the individual commits.
- **Tag releases on `main`** — see `docs/releasing.md`.

## Development Setup

```sh
# Clone and install
git clone https://github.com/tgorka/bmad-plugin.git
cd bmad-plugin
bun install

# Fast gates (no API access needed)
bun run typecheck && bun run lint && bun run validate && bun run test:unit

# Full suite, including e2e (requires the `claude` CLI and API access)
bun test
```

## Making Changes

1. Create a branch from `main`:

   ```sh
   git checkout main
   git pull
   git checkout -b feat/my-change
   ```

2. Make your changes

3. Run the gates (`bun run validate` also runs as a pre-push hook):

   ```sh
   bun run typecheck && bun run lint && bun run validate && bun run test:unit
   ```

   Never hand-edit `plugins/*/skills/`, `plugins/*/runtime/` or
   `plugins/bmad/templates/module-template/` — they are regenerated by
   `bun run sync` and the gates will catch any divergence.

4. Commit using [conventional commits](https://www.conventionalcommits.org/):

   ```text
   feat: add new skill for sprint review
   fix: correct agent prompt for quinn
   docs: update changelog
   ```

5. Open a PR targeting `main`

## Upstream Sync

This plugin tracks [bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)
as its upstream. The version is recorded in `.upstream-versions/core.json`. A GitHub Action
checks weekly for new upstream releases and opens an issue when one is found.

## Releasing

Maintainers only. See [docs/releasing.md](docs/releasing.md) for the
two-phase flow and its two current defects.

```sh
./scripts/release.sh <new-version>
```

Two known inconsistencies, documented rather than silently worked around:

- **The script still assumes the retired `dev` buffer.** It hard-errors
  on any branch other than `dev` and opens its release PR from `dev` to
  `main`, while every merged PR in this repository targets `main`
  directly. Until the script is reworked, a release has to fast-forward
  `dev` to `main` first.
- **The bump step is BSD-`sed` only** and aborts part-way through on
  Linux, leaving `.plugin-version` moved and the three JSON files
  behind. `docs/releasing.md` gives the workaround.
